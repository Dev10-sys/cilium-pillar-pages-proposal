# Observability in Kubernetes with Cilium and Hubble

## Introduction

In Kubernetes, networking failures are notoriously difficult to debug. The abstraction layers that make Kubernetes powerful—dynamic scheduling, service discovery, and ephemeral addressing—also obscure the underlying network activity.

Traditional observability tools lack the context required for containerized environments. Knowing that a packet was dropped between two IP addresses is insufficient when those IPs are reassigned every few minutes. Operators need network visibility that understands Kubernetes primitives: Pods, Services, and Namespaces.

## Limits of Traditional Network Observability

Standard tools like `tcpdump` or flow logs provide IP-level visibility. In a static environment, an IP address uniquely identifies a workload. In Kubernetes, an IP address is temporary.

To debug a failure using traditional tools, an engineer must manually correlate packet timestamps with Kubernetes audit logs to determine which Pod held a specific IP at a specific time. This process is slow, error-prone, and often impossible if the Pod has already terminated. Furthermore, packet captures do not explain _why_ the networking stack dropped a packet, only that it did not arrive.

## What Hubble Is

Hubble is the distributed observability plane for Cilium. It is built on top of Cilium and eBPF to provide deep visibility into the communication and behavior of services as well as the networking infrastructure.

While the Cilium Agent configures the eBPF datapath for connectivity and security, Hubble consumes the telemetry data generated by that datapath. It maps network events back to Kubernetes identities, providing a service-aware view of the network.

## Where Observability Data Comes From

The source of truth for Hubble is the eBPF datapath acting in the Linux kernel. As discussed in previous documentation modules, Cilium attaches eBPF programs to network hooks to process packets.

These eBPF programs naturally possess full context about every packet: key operational metadata, the source identity, the destination identity, and the policy decision (allow/deny). Hubble extracts this data directly from the execution path of the packet.

## Flow Visibility Model

Hubble represents network activity as **Flows**. A flow event captures the state of a connection attempt or data transfer.

Key flow attributes include:

- **Source and Destination Identity**: Derived from Kubernetes labels (e.g., `app=frontend`), not just IPs.
- **Verdict**: Whether the packet was `FORWARDED` or `DROPPED`.
- **Exact Drop Reason**: Unlike `tcpdump` which shows _what_ happened, Hubble tells you _why_ (e.g., "Policy X denied Identity Y").

## Common Network Problems Hubble Solves

- **L4/L7 Information**: TCP flags, HTTP methods, DNS query types.
- **Latency**: Time taken for the request and response.

## How Hubble Collects and Exposes Data

eBPF programs write flow events to a high-performance ring buffer in kernel space. This process is asynchronous and non-blocking. The Hubble agent, running in userspace, reads these events from the ring buffer.

Crucially, this architecture decouples processing from reporting. The accumulation of observability data operates independently of the packet forwarding logic.

## Hubble CLI and UI (Conceptual)

Hubble provides multiple ways to consume flow data.

**Service Map**: A visualization of the cluster topology. It displays workloads as nodes and traffic flows as edges. This allows operators to instantly see service dependencies and identify broken communication paths (often highlighted in red).

**Flow Log**: A detailed, chronological list of network events. Unlike a raw packet capture, these logs are structured and queryable by service name, protocol, or verdict.

## Debugging Common Network Problems

**Policy Misconfigurations**: A common issue is a strict `NetworkPolicy` inadvertently blocking legitimate traffic. Hubble explicitly reports drops with the reason `Policy Denied`. This confirms that connectivity exists but is blocked by configuration.

**DNS Issues**: DNS resolution failures are frequent in dynamic clusters. Hubble provides visibility into DNS traffic at Layer 7, showing exactly which queries are returning `NXDOMAIN` or timing out.

**Service Communication**: If Service A cannot reach Service B, Hubble can determine if the request is leaving Service A (egress), if it is being dropped by the network, or if Service B is simply returning 500 errors (L7 visibility).

## Relationship to Security and Policy

Observability is a prerequisite for robust security. Before enforcing a "Default Deny" policy, teams use Hubble to audit existing traffic flows. This ensures that the policy accurately reflects required application behavior.

During an incident, Hubble allows teams to differentiate between a network outage and a security enforcement action, drastically reducing the time required to identify the root cause.

## Performance and Overhead Considerations

A primary concern with observability is performance overhead. eBPF handles this efficiently.

- **No Data Path Copying**: Hubble does not copy the full packet payload to userspace (unless explicitly configured for L7 debugging). It captures only the metadata headers.
- **Efficient Buffering**: The ring buffer mechanism is low-overhead. If the userspace agent cannot keep up with the volume of events, the buffer overwrites oldest data. This ensures that observability never slows down the actual network traffic.

## Common Misunderstandings About Observability

**"Observability slows the network"**: In traditional systems where visibility requires agents/sidecars to process every packet, this is true. With eBPF, the overhead is negligible because the instrumentation is baked into the datapath logic itself.

**"Packet capture is enough"**: Full packet capture (PCAP) is heavy and often encrypted (mTLS). Hubble provides structured metadata (who talked to whom, and why) which is usually more actionable than raw bytes.

## How This Changes Operations

Incorporating Hubble changes the operational workflow for Kubernetes networking. Instead of inferring state from symptom (e.g., "The app is slow"), engineers can observe the state directly (e.g., "The app is experiencing 50ms latency on egress to the payment service").

This moves operations from a reactive, hypothesis-driven approach to an evidence-driven approach, significantly lowering Mean Time To Repair (MTTR).
